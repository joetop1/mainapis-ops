# OPS运行保障

当前仍为单实例Node.js服务，SQLite WAL持久化。此阶段增加备份、就绪检查和只读任务巡检；不自动接管或重新创建旧任务。

## 自动备份

默认正式服务启动后检查备份时间，缺少备份时立即执行，此后每24小时生成一份；失败后至少一小时再自动尝试。保留最近14份**校验通过且由本模块创建**的备份，不清理其他文件夹。手动“立即备份”也受单进程去重限制。

环境变量：`OPS_AUTO_BACKUP=false`关闭自动备份；`OPS_BACKUP_INTERVAL_HOURS`支持1–168；`OPS_BACKUP_KEEP`支持1–90。默认24小时、14份。演示模式不自动备份或开放手动备份。

备份位于数据卷`/app/data/backups/backup-时间-随机标识/`，目录权限700，数据库、密钥及清单权限600。每份包含：

- `ops.sqlite`：通过SQLite `VACUUM INTO`生成一致快照，包含当时已提交的WAL内容。
- `connections.key`：原始连接解密密钥，恢复加密商城凭据必需。
- `manifest.json`：时间和SHA256校验值；完成后验证数据库完整性。

备份由独立子进程执行，但仍可能产生短暂数据库锁与磁盘I/O。开始前检查空间；失败清理本次未完成输出，成功备份不覆盖旧快照。未完成货盘的临时预览文件、OSS图片本体、`.env`和外部商城数据库不在此备份范围。

**同盘备份只防误操作和部分数据损坏，不能防服务器或磁盘整体丢失。应将已完成备份目录定期复制到服务器外的受控位置。备份包含可解密凭据，不提供公开下载链接，不上传到商品图片公开桶。**

## 校验和恢复

校验命令（只读，不恢复）：

```bash
docker compose exec -T goods-ops node backup-data.mjs --verify /app/data/backups/实际备份目录名
```

恢复需安排维护窗口：先停止OPS、保留当前完整数据卷的副本；在离线副本上校验备份，然后将备份数据库与**配套密钥一起**恢复到新的数据卷。不要把旧WAL/SHM混入恢复后的数据库。用隔离端口验证登录、数据和连接解密后再切换正式实例。此版本未提供自动恢复按钮，也不会在启动时自动恢复。

## 运行状态和巡检

系统管理员通过“系统设置 → 运行保障”查看状态。普通团队管理员若不是系统管理员，也无法读取全局运行状态或执行备份。手动备份POST需要登录与CSRF验证。

巡检：`dispatching/accepted/verifying`超过30分钟未更新计为“超时未结束”；`unknown/awaiting_review`计为“需人工核对”。仅计数，不修改商品、任务状态、创建领取锁或回执。仍应通过现有任务列表核对商品ID，或明确重发未领取任务。

公开`/healthz`只检查进程存活；`/readyz`检查数据库可读、数据目录可写权限、32字节解密密钥文件及至少200MB数据盘空间，不连接任何商城，不暴露任务数量或备份信息。Compose使用`/readyz`，标记unhealthy不会自动触发Docker重启。

独立Worker、持久队列领取与重启恢复、跨服务器异地备份、外部告警接收端属于后续阶段，当前未实现。
