# 商城业务通知（OPS 0.7.3）

## 实际覆盖范围

会员商城 CRMEB Pro 4.3 的已验收路径：付款成功使用官方对外推送；申请退款改用官方售后列表及详情的只读补拉。以用户提供的本地 4.3 发行包 OutPushJob、OutAccountServices、OutStoreOrderServices、OutStoreOrderRefundServices 为依据。已进一步核对事件触发源码：ApplyRefund 仅发站内/notice通知，没有out.outPush；名为refund_create_push的外部事件实际在Refund处理事件中触发，而且传入订单ID给按售后ID查询的服务，不能作为可靠申请通知来源。原0.7.0仅核对接口数据结构，未确认触发点，因此未能收到客户申请。退款推送入口现只鉴权应答，不把此事件当新申请。

不是 OMS 通知连接器，多门店0.7.2和Tigshop0.7.3提供各自独立入口，需实际接口预检和付款/退款验收（见对应节）。申请退款不代表退款到账，不自动同意、拒绝、执行退款，也不写回商城。现有商品发布、n8n 与 OMS 导入不变。

## 配置

1. 在 OPS 服务器拉取并重建容器，打开「连接与配置 → CRMEB会员商城 → 查看配置 → 企业微信群通知」。选择对应的具体商城连接。
2. 在密码框粘贴内部群自定义消息推送 Webhook；勾选启用与订阅事件并保存。Webhook 加密保存，不通过GET返回。
3. 点击「发送测试通知」，等待数秒查看群，再刷新通知记录。需要 OPS 进程常驻；工作进程每4秒最多尝试1条，单实例最多15次/分钟，不开启 n8n 重复转发。
4. 复制页面下方生成的推送配置到 CRMEB 对外接口应用的推送设置。建议单独创建通知专用应用，避免覆盖原 OMS 或其他系统的推送地址；只开推送，不额外授予商品写入权限。

| CRMEB 字段 | OPS 页面提供值 |
| --- | --- |
| push_account 推送账号 | 推送账号 |
| push_password 推送密码 | 推送密码 |
| push_token_url 获取Token地址 | 获取Token地址 |
| order_pay_push 订单支付推送 | 订单支付推送地址 |
| refund_create_push 售后单生成推送 | 售后单生成推送地址 |
| order_create_push / refund_cancel_push / user_update_push | 其他事件地址（只鉴权应答，不通知） |

地址必须完整粘贴，不手工追加查询参数。CRMEB 保存后启用 push_open，同时其接口应用自身应启用；需商城原队列工作进程运行。
推送账号密码由OPS生成，与商城接口AppID/AppSecret及企微Webhook完全不同。只在登录的管理员配置接口返回，供直接复制到商城，不要发到聊天或公开日志。

## 协议兼容

接收路径：`/api/notification-push/<稳定商城连接ID>/token|paid|refund|ignore`。
- 原生后台「测试获取Token」用 GET 携带 push_account/push_password，要求 JSON status=200/data；队列实际用 POST JSON，要求 code=0、token/time。OPS 同时返回两种兼容结构。
- Token 为每连接独立密钥签发的带时效令牌，只允许当前连接接收；实际回调用 `?pushToken=...`。令牌每次调用校验，不依赖登录Cookie。
- 收到事件必须先通过认证、字段校验，并成功持久化入队后，才返回 code=0；企微发送由独立定时worker完成，不让外部消息平台故障阻塞商城请求。
- 以连接+事件类型+订单/售后内部ID去重，重复推送不会创建第二条提醒。忽略事件只返回成功，不保存用户余额等无关资料。

原生协议会在GET查询串放推送账号密码，以及在回调查询串放Token。OPS应用不记录请求URL、正文、密钥；网关/反向代理对该前缀应使用不含查询串的日志格式或独立关闭访问日志，避免凭据进入访问日志。不要将配置页和Token响应截图公开。

## 消息与可靠性

消息只提取订单/售后编号、金额、前5项商品名称/规格/数量、退款原因和事件ID，不保留回调原文、发票、完整姓名、电话、地址。自由文本中的手机号和链接进行遮盖。金额按该CRMEB版本人民币口径显示CNY，不转换OMS/Tigshop币种。发送文本最多1950 UTF-8字节，超过时缩略；完整明细到商城后台查看。

队列保存在原OPS数据卷内的SQLite。企微明确非零错误按指数退避自动重试，最多5次，错误码可见。网络超时、无效响应、发送中进程重启均标为「需核对群消息」，不盲目自动重发。管理员核对群中是否已收到后可手动重试；存在网络不确定性，不宣称外部消息端到端严格恰好一次。

暂停接收与发送会保留并暂停待发送队列，恢复后继续。已有待发送/暂停/不确定业务通知时不允许更换群地址，避免将历史业务投递给新群。退款优先于付款。通知发出与否不改变商城订单、售后状态。

仅管理员管理密钥、发送测试和重试；其他团队角色不可读取配置。连接ID稳定，个人迁入团队后设置与回调归属仍跟随该商城连接。

## 验收与限制

自动测试覆盖推送身份、跨连接隔离、GET/POST Token兼容、过期令牌、持久去重、脱敏、拒绝重试、超时不确定处理、暂停恢复、字符长度、CSRF和角色权限。尚未使用真实Webhook向企业微信发送，需先点页面测试，再用一笔真实测试订单核对付款与退款申请。付款暂未配置补拉补漏，CRMEB自身重试次数有限；退款补拉行为见下节，仍应保留商城后台日常核查。部署为单OPS实例，不能未经设计扩成多发送实例。

## 退款申请补拉（0.7.1）

更新OPS后，通知配置页点击「检查并补拉近24小时退款申请」。使用OPS上方已保存的商城AppID/AppSecret获取token，与推送接收账号密码不同。需为这个商城API应用增加 **GET /outapi/refund/list** 和 **GET /outapi/refund/:order_id** 的只读权限；不需要退款执行权限，也不修改商城源码或队列。

先预检列表和首条详情，成功后记录独立通知补拉状态并异步扫描。首次手动操作补发最近24小时未取消、未删除且refund_type为0/1/2/4/5的申请；后续每分钟按上次成功检查时间、重叠5分钟扫描。列表返回的refund_price会被官方改名pay_price，因此进一步读取详情中的refund_price；原订单号取官方orderData绑定的store_order_sn，不把售后单号误当原订单号。详情ID、售后单号和原订单内部ID与列表再次核对。申请金额、明细清洗后写入同一通知去重队列。

每轮最多20页、每页50条；未完整扫描、权限不足、数据格式异常不会推进成功时间，配置页显示错误。超过扫描上限需要人工核对积压量，不能宣称无遗漏。关闭总通知或退款订阅时停止拉取。仍只提醒申请，不执行退款；已处理的售后不会作为新申请发送。

CRMEB真实事件触发问题已定位于用户提供的4.3源码，线上具体文件若有差异可另行只读核对。本修复自动测试通过，真实售后读取权限和企业微信群补拉效果仍需更新后点击检查按钮验收。

## 多门店通知入口（OPS 0.7.2）

新增「CRMEB 多门店 → 查看配置 → 企业微信群通知」，与会员入口完全独立。可手动填写同一企业微信群Webhook，但不自动继承接收群、开关、推送账号密码或通知记录。每个具体商城连接均有单独令牌和回调地址，同一订单ID在不同商城不会相互去重。

多门店读取使用既有已验证的 `/outapi/get_token` 鉴权，不能使用会员的 `/outapi/access_token`；退款补拉严格要求售后列表/详情协议、关联订单号、时间及金额与适配契约一致。接口预检失败不会启用补拉，错误在配置页显示。不放宽为猜测ID或把其他商城凭据作为回退。

多门店启用流程：保存本商城通知设置 → 发测试消息 → 把本商城生成的推送配置填入多门店后台 → 测试一笔付款 → 检查并补拉近24小时退款申请。可继续使用同一群，消息以商城自定义名称区分。无需更新n8n、采集插件或商城源码。原会员已启用的配置和补拉状态保持不变。

本地已核对完整源码为Pro4.3，尚无已部署多门店4.2完整推送源码副本，因此多门店事件触发不能仅由会员源码推断；兼容逻辑用固定只读接口预检和用户实际付款验收确认。185项自动测试包括不同系统/连接隔离、多门店get_token路径、实际handler的售后预检入队、两个表单与复制按钮互不串数据；多门店真实推送及售后格式仍待上述上线验收。若格式不符，应取得对应版本相关源码再补适配，不修改商城核心。

## Tigshop 自营通知（OPS 0.7.3）

入口：连接与配置 → Tigshop → 查看配置 → 企业微信群通知。独立保存接收群、订阅开关和检查进度，不继承CRMEB密钥。使用该具体商城连接已保存的API Token读取数据，始终X-Api-Token / X-ADMIN-TYPE=admin，不使用CRMEB推送账号，不要求商城回调、不依赖OMS/n8n、不修改商城原文件。

配置时须显式填写接口金额基准币种（ISO货币代码，如EUR）和接口格式化日期所在IANA时区，均无猜测默认值。不是顾客前台切换的显示币种，不采用商品发布汇率重新折算订单金额。保存并发群测试后，点击「检查接口并补拉近24小时通知」启用选中事件。首次手动检查补发近24小时符合条件的自营已付款订单、平台待审核售后；之后每分钟继续，保留5分钟重叠窗口。通知中的时间统一标注北京时间。

已审阅本地Java 5.8.32的OrderController、AftersalesController、OrderVO、AftersalesVO、OrderItemVO、AftersalesItemVO、PaymentStatus、AftersalesStatusEnum、对应服务及BasePage排序实现，并参考既有ONEX的只读订单客户端；线上版本字段和权限仍以实际预检为准，不据本地源码宣称现网接口已经验证。若格式不同，停止并显示错误，取得该版本字段再适配。

只允许下列GET读取：

- `/adminapi/order/order/list?page=...&size=50&sortField=payTime&sortOrder=desc&shopId=0&payStatus=2`
- `/adminapi/order/order/detail?id=...`
- `/adminapi/order/aftersales/list?page=...&size=50&sortField=addTime&sortOrder=desc&shopId=0&status=1`
- `/adminapi/order/aftersales/detail?id=...`

需API Token具备订单、售后列表和详情读取权限，不需退款、审核、发货等写权限。保留重定向拒绝、HTTPS公网域名检查和DNS固定解析。不读取财务refundApply来替代客户申请。

付款判断使用订单PaymentStatus（2=已支付），不能错用另一个PayStatusEnum的1。按付款时间排序和检查，因此较早创建、刚付款的订单也可捕获。详情再次核对订单ID、订单号、自营shopId=0、有效性和状态，使用paidAmount显示实际支付。失效拆单父单不提醒，子单按其实际订单ID分别去重。

退款提醒仅针对平台待审核status=1、aftersaleType=1/2。核对售后ID/单号、关联订单ID及原订单号，关联订单也必须自营。金额取refundAmount，数量取售后项number（不是原购买quantity）。已拒绝、取消、完成以及已通过审核进入后续处理的售后不作为新待审核申请。若短时间内已处理完毕，轮询可能看不到中间状态；这是状态读取，不是完整事件审计。

列表即使忽略shopId=0查询条件，也会在本地和详情再次确认，不能把其他商户消息发到自营群。付款和退款进度分开，每轮每类最多20页，不完整、乱序、时区异常、缺字段或权限失败时不推进成功时间，页面可查看原因。格式化时间严格按所选时区解析，夏令时重复/不存在的时间不能可靠确定时会停止，不默默猜测。配置地址/币种/时区变更后须重新预检；待发送业务未处理时禁止更换其解释口径。

复用持久去重、脱敏、发送队列和失败/不确定状态处理。测试覆盖Tigshop与CRMEB配置隔离、显式币种时区、真实handler预检入队、仅GET、他店过滤、支付中与售后状态区分、旧单新付款、关联核对及扫描上限。195项测试通过；真实Tigshop订单接口及群通知仍需上述页面预检和单笔验收。

## 0.7.4 多门店原生通知转接

实际多门店源码的付款给客服、申请退款给客服事件均已接企业微信通道，但只传订单号。
本版本沿用 EnterpriseWechatJob 的 markdown POST 协议，新增 OPS 接收和资料补全，不修改商城源码或 n8n。
会员商城与 Tigshop 通知流程保持原状；多门店旧退款定时补拉停用，避免继续调用缺失 orderData 关联的售后详情。

更新后在 OPS → 连接与配置 → 多门店 → 企业微信群通知保存群 Webhook 并启用。
先发送测试通知，再点「检查通知读取权限」，然后把页面提供的两个专用地址和两个模板复制到商城：

- ID 19「下单给客服发消息」实际为付款事件：付款地址及付款模板。
- ID 18「申请退款给客服发消息」：退款申请地址及退款申请模板。

模板分别为单行 OPS_PAID|{order_id} 与 OPS_REFUND|{order_id}。保留占位符，不加标题、空格或换行。
商城原先直发企业微信群的这两项改为 OPS 专用地址，其他通知项不变。群 Webhook 仅保存在 OPS。
接收地址含独立密钥，不要分享截图。反向代理对此路径应使用不带查询字符串的访问日志，
例如 Nginx $uri，不使用 $request_uri 或 $request，以免日志保存密钥。

入口只接受 POST 原始 JSON（兼容原生 HttpService 未指定 JSON Content-Type），最大8KB，
先校验密钥、事件和模板，再将最小接收记录持久写入 SQLite，最后应答。
后台按订单号读取订单详情并核对原订单号与内部 ID；付款校验已付款状态并取真实实付金额、商品和规格。
退款另读售后列表，按原订单内部 ID 关联，只取售后自身的申请金额、商品数量、原因和售后号，
不用实付金额代替退款金额，不调用售后详情接口。退款每次最多20页、每页50条，
只提醒接收时间前24小时内仍待处理的申请；列表排序、关联或字段错误时不入队部分结果。
同一订单后续出现新售后号仍可发送；付款按原订单ID、退款按售后ID持久去重。

应用需具备订单列表（权限预检使用）、订单详情及售后列表只读权限。没有商城写入操作。
预检和群测试不等于真实事件验收：配置后需做普通商品付款、申请退款各一笔测试。
付费会员等非普通商品订单若该订单详情接口不支持，会显示读取错误，不猜测补全。

「商城原生接收记录」与「最近通知记录」分开显示：前者是接收/资料读取，后者是发群结果。
读取失败最多退避重试8次，最终失败可手动重试读取；收件及发件按业务ID去重，
重启恢复读取任务，入队与收件完成状态在同一事务内。暂停通知保留待处理收件。
有未处理收件/发送任务时禁止换群。群发送结果不明确仍需人工核对，不能宣称端到端恰好一次。

商城原生任务忽略HTTP回执、总返回成功，OPS停机或地址填写错误期间的事件不保证重传。
本方式仅接收配置后原生触发的事件，不补发历史付款。读取失败显示在 OPS；
如果完全没有接收记录，应检查商城地址、模板、通知开关和商城队列。

自动测试覆盖鉴权隔离、原生非JSON Content-Type、持久接收、重复通知、同单多售后、
读取失败、停止旧补拉、部分入队回滚、重启恢复和页数上限；真实接口与群送达仍需上线验收。
