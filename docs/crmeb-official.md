# CRMEB 官方接口接入 · v0.2.0

本方案只修改 OPS 和 n8n，**不向 CRMEB 新增 PHP、路由或配置文件**。此前的候选自定义连接器已从当前版本移除（Git 历史仍保留）。用户已验证官方 Token 与分类详情接口可用；实际创建商品仍待联调。

## 当前已确认的接口能力与限制

- Token：`POST https://xlupw.com/outapi/access_token`，参数 appid/appsecret。已有 n8n Custom Auth 凭据可直接复用。
- 创建：`POST https://xlupw.com/outapi/product`，Bearer Token 认证。
- 详情：`GET https://xlupw.com/outapi/product/{id}`。
- 分类 116 已确认存在，父级 115，名称“炮机”。该 ID 只用于此已确认分类，不应套用到其他商品。
- 用户提供的版本，新增成功只返回消息，未返回新商品 ID；列表接口强制筛选已上架商品，因此不能用列表自动查回下架商品。
- 对外分类列表实现强制 pid=-2，曾在线上返回空列表。OPS 新版通过商城前台 `/api/category` 读取可见分类树、`/api/brand` 读取已上架商品使用的品牌，不修改商城；未选 ID 的历史任务仍兼容名称映射。
- 原商品保存会对相同 `soure_link` 自动转为更新，因此本流程发送 `soure_link=''`。真实来源链接只保留在 OPS 不可变任务快照中，以任务编码关联；不将批发链接暴露给商品消费者。
- 图片使用运营提供的 HTTPS 地址，当前不下载、不转存、不处理防盗链、不宣称图片已存到商城。首测请用商城图床/自有存储中的可用图片。实际图片显示仍需人工检查。

## 首次更新

在 OPS 服务器运行（不要进入商城目录）：

```bash
cd /www/wwwroot/mainapis-ops
git pull --ff-only
docker compose up -d --build
```

数据库增加任务快照表，原商品、任务、会话保留。不要删除卷。旧版本联调失败任务保留；新建任务才有新的快照和领取协议。没有快照的历史任务不能通过新流程重放。

## 导入官方工作流

从 Mac 本地或 GitHub 下载 `workflows/publish-crmeb-official.json`，在 n8n 导入为新工作流，不覆盖已验证的手动读取测试流程。

此工作流默认未发布，生产路径 `webhook/ops-crmeb-official`，不会与旧的 `goods-ops-publish` 冲突。

配置以下三处：

1. **接收 OPS 官方接口任务**：选择已有 Header Auth 凭据（Name 为 `X-Ops-Token`）。
2. **获取 CRMEB Token**：选择已经测试成功的 Custom Auth 凭据（body.appid/body.appsecret）。不要将密码填到普通 Code 节点，不要将 Token 输出截图上传。
3. **配置分类运费并转换字段**：在代码靠下的 `const config=...` 位置填写映射与真实运费模板 ID。例如下面的 7 只是格式示例，不是真实模板 ID：

```javascript
const config={categoryMap:{'炮机':[116]},shippingTemplateId:7};
```

原文件中的 shippingTemplateId=0 会阻止创建，必须用商城真实的运费模板 ID 替换。使用此分类时，OPS 商品分类文本填写“炮机”。后续按同样格式增加其他已确认分类。核验节点自动复用该配置，不用填两遍。不要为了测试将商品设为包邮。

工作流保存、Publish 后，在 OPS `.env` 中更新：

```dotenv
N8N_WEBHOOK_URL=https://n8n.mainapis.com/webhook/ops-crmeb-official
```

`N8N_WEBHOOK_TOKEN` 继续使用原 OPS→n8n 密钥，Casdoor 配置不变。环境变量更新后执行 `docker compose up -d --force-recreate`。

旧的三节点联调工作流可以保留但不再使用其 URL。不要导入历史 `publish-crmeb-pro.json`，它属于已停用的自定义接口方案。

## 实际使用

1. 在 OPS 添加真实商品资料、图片与 SKU。新版在商品编辑页从商城选择分类，保存真实 `category_id`；历史名称分类需重新选择，历史任务仍使用旧映射。SKU 编码为 1–64 位字母/数字/点/短横线/下划线，不允许重码；规格文本不得含英文逗号、分号、等号。当前一行组合规格作为“规格”维度保留，重量体积默认 0。
2. 审核后选择 CRMEB 会员商城发布。
3. n8n 获取可信快照、校验字段和授权，紧接新增调用前向 OPS 领取一次性创建权限。相同 job_id 只领取一次，不自动重试写接口。
4. 官方返回 200 后显示 **待核对商品ID**，不增加成功数。
5. 打开商城后台仓库中的下架商品，按商品名或 OPS 任务编码查找。任务列表显示完整编码 `OPS-...`，对应商城商品编码 `code`。复制真实商品 ID。
6. OPS 任务列表点击 **填写商品 ID 核对**。n8n 只 GET 详情，核对商品 ID、任务编码、下架状态、标题、分类、SKU 编码/规格/价格/成本/库存；一致才记为成功。填错只返回待核对，不会更新或创建商品。
7. 图片与运费设置仍需在商城人工检查；当前流程不进行上架。

## 重复、超时和失败处理

- 在一次性领取之前（例如凭据或映射未配置）失败，任务可能仍显示执行中。修正 n8n 配置并 Publish 后，在 OPS 点击 **重发未领取任务**。同一 job_id 的创建领取仍只能成功一次。
- 领取后任何超时或结果不明都不能重新创建；先到商城仓库核对，再用商品 ID 做只读核验。
- 只修改 OPS 商品资料不会解除已领取创建任务的限制；首版不支持自动更新已创建商品。不要通过新建任务、重复执行 HTTP 节点等方式绕过限制。
- n8n 执行历史可能显示失败，而 OPS 显示执行中/需核对，这是结果未知时的保守状态，不代表商城一定没创建。
- 核验请求每次使用独立 nonce，旧的核验结果不能覆盖新的核验请求。
- 默认不保存 n8n 成功/失败/手动执行数据，避免官方 Token 响应中的 appwd 字段进入持久执行记录；管理员调试时仍能看到敏感响应，应避免截图。
- 不要在 n8n 手动只重执行“官方新增下架商品”节点，它会绕过前面的 OPS 一次性领取检查；测试请从 OPS 发起。

本地测试覆盖字段转换、一次性领取、授权隔离、旧核验回调拒绝、创建200不误报成功、真实详情比对与生成工作流结构。运营者已在线上完成商品 553 的创建和核验。新增的品牌、商品标签、虚拟销量经过本地测试，尚未线上验证。

## 品牌、商品标签和虚拟销量

商品编辑页从服务器读取会员商城分类和品牌供选择，保存 `category_id`、`brand_ids`。分类显示完整层级路径；品牌可不设置。`tag_ids` 暂仍填写商城已有 ID，`virtual_sales` 可编辑。发布分别写入 `brand_id`、`store_label_id`、`ficti`，真实销量 `sales` 保持 0，不使用用户标签字段 `label_id`。这些字段会保存在任务快照中，修改商品后需要重新审核，不会自动更新已创建商品。

更新已有 n8n 工作流时，将新 JSON 临时导入为未发布工作流，仅把其中“配置分类运费并转换字段”和“核验实际入库结果”的 JavaScript 复制到当前工作流同名节点。前者底部 config 中的 `shippingTemplateId` 恢复为线上值 1，并保留现有分类映射。发布当前工作流即可，不需要改动凭据或 Webhook。模板运费 ID 为 0，会阻止未配置的创建请求。


## 升级商城分类和品牌选择

OPS 后端固定请求 `https://xlupw.com/api/category` 和 `/api/brand`，浏览器只访问 OPS，不需新的商城密钥。结果缓存 5 分钟，编辑页可点「刷新商城分类与品牌」。读取失败会明确显示，不能伪装为空列表。保存、审核、发布前校验所选 ID，分类名称由服务端列表确定，不信任客户端输入名称；会员商城分类不能用于其他商城。

范围限制：仅有前台可见分类，以及当前上架商品使用的可见品牌；没有使用中的品牌可能返回空列表，不等同后台没有品牌。本版不读取商城数据库或管理员账号，也不承诺获取全部后台品牌。此接口读取已核对商业源码，但尚未在线上浏览器验证；部署后先检查列表。

已有 n8n 工作流只需在「配置分类运费并转换字段」「核验实际入库结果」两处搜索并替换下面一行，发布当前工作流，保留原凭据和运费模板配置：

旧：`const ids=config.categoryMap?.[p.category];`

新：`const ids=Number.isSafeInteger(p.category_id)&&p.category_id>0?[p.category_id]:config.categoryMap?.[p.category];`

新选中的分类不再需要名称映射；旧快照没有 category_id 时仍用原映射。已创建的任务保持原快照，编辑商品不会自动改变历史任务。不要重复执行商城新增节点。


## SKU 对应图片

原版发布统一使用商品首图，已修正为 `skus[].image` → CRMEB `attrs[].pic` / `attr.pic`，同时写入规格项图片。没有 SKU 图片的旧资料仍回退商品首图，不能凭主图顺序猜匹配。带 SKU 图片的新快照会额外核验官方详情中的 SKU 图片地址；实际可访问性和画面内容仍需人工检查。

1. 重新加载采集插件 0.1.4，在 1688 当前商品页采集并核对每个规格缩略图。下载 JSON。
2. 更新 OPS 容器。在原商品编辑页选择「导入已采集的 SKU 配图」，只更新同来源、同编码的图片，不改售价/库存。没有图片的 SKU 可手工填 HTTPS 地址。
3. 将最新 `workflows/publish-crmeb-official.json` 临时导入为未发布工作流，把「配置分类运费并转换字段」「核验实际入库结果」两个节点代码完整复制到线上同名节点。保留线上 config（尤其运费模板 1 和历史分类映射），然后 Publish。不要发布临时副本，避免重复 Webhook。
4. 已在商城创建的商品不会自动更新；当前仅支持创建，不能通过重新发布或重复执行新增节点来补图。已发布商品应在 CRMEB 后台修改规格图片；若要批量自动修复，需另做仅更新图片的专门流程，不能把整件商品重新创建。
