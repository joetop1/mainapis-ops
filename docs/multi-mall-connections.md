# OPS 0.5.0：多商城连接基础

## 本次范围

固定商城系统类型和具体商城连接独立。一个团队可以添加多个同类型商城，连接拥有稳定 ID、自定义名称及独立凭据。芸众、Tigshop 和新增 CRMEB 连接使用各自公网 HTTPS 域名；仍仅支持已核验的接口协议版本。芸众扩展商城账号仍固定 i=1，Tigshop 当前适配欧元商城。

新增 CRMEB 连接由 OPS 直连既有 /outapi 接口，运费模板 ID 在页面明确填写，需要商家在商城核实。创建接口未返回商品 ID 时保留领取锁，要求填写商品 ID 核对后才可成功。原 CRMEB 连接继续走原 n8n 工作流，其原域名和工作流不自动改写。新增连接不使用服务器环境变量中的 Webhook 或其他商城凭据。

同系统下相同已配置域名不能再次配置为另一连接。已有发布历史的连接不能改变域名，应添加新连接。允许改名、密钥轮换；不删除历史任务。

## 数据与兼容

- 新增 mall_connections；jobs 新增 mall_connection_id，活动任务唯一性按商品版本、系统、具体连接约束。
- 老任务原位补充旧连接 ID，保留任务 UUID、货号、商城商品 ID、回调令牌、原冻结快照及原状态（既有重启恢复规则仍将执行中的任务标记待核对）。
- 旧凭据继续使用原加密 scope；新增连接使用 mall:<连接ID>，不与默认连接共用。
- 个人转团队时连接 ID 不变，新增连接凭据 scope 不变；旧凭据沿原团队迁移逻辑复制。
- 分类、品牌缓存按 owner + connection_id 隔离。商品整理记录保留 catalog_connection_id，任务按连接去重，发布摘要分别记录每个连接。
- 老 API 未传 connection_id 时继续使用该系统历史默认连接。新界面显式传递 ID；其他团队或错误系统的 ID 均被拒绝。
- 发布任务绑定连接，旧快照缺少地址时仍按原历史地址核对。新增 CRMEB 任务冻结 origin 和 shippingTemplateId，使用原经过校验的字段构建器及读回核对器。

本阶段仍是每件商品当前整理一套商城分类/价格配置。发布到另一商城时，在编辑页切换具体连接、重选分类品牌、保存并重新审核；已有发布历史保留。为同一商品同时保存多份商城分类/价格覆盖配置属于下一阶段，不自动复用不同商城的分类数字 ID。

## 界面

连接与配置 → 添加商城 → 选择固定系统、填写商城名称 → 对应系统卡片中切换“当前商城连接” → 填写本商城地址和凭据 → 测试/保存。

编辑商品 → 选择系统和具体商城连接 → 从该连接读取分类品牌 → 审核 → 发布。采集箱徽章及发布任务按具体商城名称显示。管理员可以添加/配置，编辑员和审核员不能修改连接。

## 部署（OPS 服务器）

先构建，停止期间备份完整数据目录（包括 SQLite WAL/SHM 与 connections.key），再启动。勿上传备份到公共文件服务。

```bash
cd /www/wwwroot/mainapis-ops
git pull --ff-only
docker compose build
backup_dir="backups/pre-0.5.0-$(date +%Y%m%d-%H%M%S)"
mkdir -p "$backup_dir"
chmod 700 "$backup_dir"
docker compose stop goods-ops
docker compose cp goods-ops:/app/data "$backup_dir/"
# 仅确认备份成功后继续：
docker compose up -d
docker compose ps
```

首次升级时，程序还会在原 SQLite 路径旁以 VACUUM INTO 自动生成 `.pre-mall-connections-时间戳.sqlite` 一致性快照，并设为0600。自动快照不替代完整数据目录备份，因为解密仍需要原 connections.key。

不需更新浏览器插件或芸众扩展。新增连接需先用一件测试商品下架入库，人工检查图片详情、SKU、价格库存和运费。

不可只回滚代码：旧版唯一索引无法表示多个同系统商城任务。需要回滚时，先停止服务，保全升级后的完整目录，再成套恢复升级前数据库/密钥和对应旧版本代码。恢复旧备份不会撤销已写入商城的商品；升级后产生的任务回执须保留并人工核对，不可盲目重发。

## 验证证据

150 项自动化测试通过；含旧库升级备份、稳定 ID 和团队迁移、跨团队拒绝、同系统双商城完整发布、连接独立签名/分类/商品ID/去重、域名重复与发布历史保护、新 CRMEB 域名与运费直连、写入超时保锁、过期核对不能覆盖、旧工作流回归。

jsdom 全应用启动与交互检查通过：同系统第二商城切换、配置请求携带连接ID、编辑页连接选择及分类请求绑定。未完成真实浏览器截图验证、真实客户新域名联网或真实商城新增写入验证；部署后按上面的单件验收流程完成。
