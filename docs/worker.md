# 独立发布Worker（0.13.0）

## 部署结构

Compose服务：

- `goods-ops`：登录、页面、商品编辑、审核、持久队列提交、结果回调、备份及现有通知轮询。
- `worker`：消费发布和商品ID核对队列，执行现有商城适配器或派发到旧n8n工作流。图片转存随发布任务在此执行。

两者使用同一个**主机本地**数据卷`goods_ops_data`和SQLite WAL。没有新增Redis、外部数据库或公开Worker端口。当前只有一个有效执行者，其他Worker等待租约；直连任务串行处理，n8n内部任务的并发仍由n8n管理。供应商货盘预览/导入、通知轮询及备份调度未在本阶段迁入发布Worker。

Compose为两者设置`OPS_DURABLE_QUEUE=true`。直接用Node运行时须为网页服务和Worker都设置此变量，分别运行`node server.mjs`与`node worker.mjs`。不设置时网页保留单进程兼容模式；不要在有待执行任务时随意切换模式。演示模式不执行商城任务，Worker空闲待命。

## 更新和检查

```bash
cd /www/wwwroot/mainapis-ops
git pull --ff-only
docker compose up -d --build
docker compose ps
```

必须启动**整个Compose项目**，不要只更新`goods-ops`。Worker在网页就绪后启动；无独立端口，健康检查读取数据库心跳。

“系统设置 → 运行保障”显示Worker在线状态、排队数、执行数和中断待核对数。

```bash
docker compose logs --tail 50 worker
docker compose exec -T worker node worker.mjs --check
```

## 持久化与恢复边界

- 新任务、商品快照、图片转存计划和队列项在同一数据库事务提交。
- 未领取的排队项在重启后继续执行；不会丢失在内存回调中。
- Worker通过数据库租约取得唯一执行权，每5秒续约。失联后最长约120秒才允许另一执行者接手；此间排队等待，不在网页进程兜底创建。
- 接手时将旧执行中的队列项标记中断。发布任务标为“需核对”，核对任务回到待人工核对；**即使创建领取锁仍为0，也不自动重发已经开始派发的任务**，因为旧n8n或商城可能已接收请求。
- 已成功/失败的终态不被中断处理覆盖；已领取创建的任务绝不释放创建锁或重新创建。
- 商品ID核对保留原nonce隔离，过期请求不覆盖新结果。
- 原有未领取任务的人工重发仍可使用，入队前再次校验创建锁及运行状态；执行中的请求不接受重发。

网页服务重启不会修改正在排队或Worker执行中的任务。Worker优雅退出会等待当前操作；Compose给予45秒退出窗口，超时被终止时按中断规则处理。不要用重启次数来判断商城是否创建成功。

## 升级前已有任务

旧版遗留的执行中任务不会批量自动迁移或重新创建，沿用原有人工核对入口。历史n8n连接继续可用，无须更新n8n代码或商城扩展。

建议在当前没有正在创建商品时首次升级。升级后先确认Worker在线，再提交一件测试商品验证回传和实际入库，确认后使用批量发布。

## 回滚

先停止Worker，并核对正在执行的商城任务。保留数据卷和更新前备份；不要删除队列、创建领取锁或使用`down -v`。待处理任务不会因切换旧代码而安全消失，不能把“回滚成功”当成“可以再次创建”。建议优先恢复当前Worker服务，让排队任务继续；需要切回单进程时，应先确认队列没有运行/排队项，并对中断任务逐一核对。

本阶段的持久队列仍是单主机架构，不代表跨主机多副本、高可用或无限并发。

## 旧备份恢复时必须先暂停

恢复过去的数据库可能把真实已经执行过的任务恢复为“尚未领取”。在恢复数据后启动任何服务前，先在`.env`设置`OPS_WORKER_PAUSED=true`，重新创建两个服务。暂停时Worker不领取任务，“运行保障”显示已暂停。必须先对备份中的排队/执行中任务逐一核对商城和n8n记录，确认不会重复创建后再恢复执行。不要直接启动默认未暂停的Worker消费旧备份。暂停不等于取消商城或n8n已经接收的操作；计划维护时仍应先等待在途操作结束。
